# Pattern Supplement: scrollytelling

`scrollytelling` 是一种按离散步骤推进理解的章节模式。它适合把同一组证据拆成几个连续的认知动作，让读者先看到基线，再逐步看到差异、异常、原因或结论。

## 适用场景

- 同一章里需要按顺序揭示信息，而不是一次性把所有信息堆给读者。
- 同一张主图需要随步骤推进而变化，但章节的核心问题保持一致。
- 这一章的重点是“带着读者一步步理解”，而不是只给出一个静态结论。

不适用的情况：

- 章节只有一个静态结论，用一张图直接讲清就够了。
- 所谓步骤只是把一段话拆成几屏，但图表没有随之推进。
- 每一步都在切换完全不同的问题，导致章节失去单一认知任务。

## 图表跟步模式

下面四种模式是常见的推进母型，不是互斥枚举。一个 scrollytelling 章节可以组合使用它们，例如先逐层构建，再时间段扩展；关键不是给整章贴唯一标签，而是让每一步都写清三件事：比上一步新增了什么、读者现在该看哪条证据、这条新增证据如何推进判断。

### 逐层构建

适合从简到繁建立理解的章节。

- step progression：先给出基线视图，再逐步增加系列、对照、趋势线或标注。
- 常见节奏：先看总体，再加分类；先看主线，再加转折；先看原始走势，再加结论提示。
- plan 写法重点：每一步都要写清新增了哪一层系列、对照、趋势线或标注，读者现在该看哪条新增证据，以及这条新增证据如何把判断从“基线”推进到“更完整的理解”。
- 数据要求：如果后续 step 会引入新的系列、对象、对照维度或新的排序结果，应为对应 step 绑定自己的 `dataRef`；不要默认复用只包含基线状态的数据。

### 聚焦-展开

适合先锁定异常，再逐步解释原因的章节。

- step progression：先把注意力收缩到异常点或异常区间，再补上下文、对照或原因解释。
- 常见节奏：先指出异常，再说明它发生在哪一段，再引入对照对象解释差异。
- plan 写法重点：每一步都要写清当前聚焦对象、这一步新增了什么上下文，以及这段新增上下文如何改变对异常或问题的判断。

### 分组对比

适合需要分批引入多个对象做对照的章节。

- step progression：先给出主对象，再逐步引入其他对象，最后落到差异结论。
- 常见节奏：先看 A，再加 B，再看 A/B 差异；先看核心组，再引入外围组做层次对比。
- plan 写法重点：每一步都要写清新增了哪个对象或组、读者现在该看哪组差异，以及这个新增对象为什么会改变对主对象的判断。

### 时间段扩展

适合同一条时间序列需要按阶段逐步展开解释的章节，例如线图、面积图或累计走势。

- step progression：先给出起始时间段建立基线，再逐步向后补充新的时间段，让读者随着时间推进看到走势如何变化。
- 常见节奏：先看早期走势，再补中段转折，最后补最近阶段并落到结论；或者先看平稳期，再补快速变化期，最后看回落或恢复期。
- plan 写法重点：每一步都要写清新增了哪一段时间、读者现在该看这段新增走势里的什么证据，以及这段新增时间如何改变对整体趋势的判断；不要只是机械地把时间轴拉长。
- 数据要求：每个 step 必须绑定自己的 `dataRef`；各 step 字段保持一致，只随着时间范围向后扩展，数据量逐步增加。

## Step-level `dataRef` 规则

- `step-level dataRef` 是否需要，不按模式名决定，而按当前 step 的图表输入是否真的变化来决定。
- 如果各步共享同一份数据输入，只是高亮、annotation 或叙述重点不同，可以继续复用 chart-level `dataRef`。
- 如果某一步新增时间段、系列、对象、对照组、过滤条件，或发生排序变化、排名重排、对象顺序变化，就应为该步准备对应状态的数据，并绑定自己的 `dataRef`。
- 如果某一步的核心变化是排序或重排，直接准备已经按该步目标顺序排好的数据；不要复用同一份原始顺序数据，再期待运行时自动体现重排。
- 组合模式按 step 判断：同一章可以先逐层构建，再时间段扩展；也可以先聚焦异常，再引入新的对照组或排序变化。判断标准始终是“这一 step 的 chart input 是否真的变了”。

## 写法提醒

- 章节仍然需要一个明确的 section title；scrollytelling 可以省 chart title，但不能省章节标题。
- 主图 chartType 只允许 `line / area / column / columnPercent / bar / barPercent / columnParallel / barParallel / dualAxis`；`heatmap` 等密集矩阵图不适合作为滚动推进主图。
- `Steps` 是认知推进单元，不是排版切片。
- - 每一步都应伴随明确且可感知的图表状态变化；step narrative 只写三件事：这一步比上一步变了什么、读者现在该看哪条证据、这条新增证据如何推进判断。第一可以是 baseline；从第二步开始，每一步都必须通过 `dataRef`、`highlightDesc` 或 `annotationList` 写出明确且可感知的图表状态变化。只有 `title` / `narrative` 的 step 不会改变 VSeed 输入，会生成假 scrolly。
- step narrative 只解释当前 sticky 主图在这一 step 能表达的证据；不要在同一步里引入另一张图、另一个问题，或与当前主图状态无关的结论。
- 如果某一步没有新的视觉推进，就不应该单独成步。
- 默认数值标签走 renderer / build 默认逻辑，不要在 Step 中切换标签策略，也不要用 annotation 模拟默认标签。
- Step 里的 `highlightDesc` / `annotationList` 只描述当前步新增的视觉推进，不要把整章所有标注一次性堆进第一步。
- Step-level `type: point` 沿用 [chart-contract.md](chart-contract.md) 的定位写法：`point.target` 直接写维度 id，并且总是带 `measureId`
- Step-level `type: difference` 也沿用通用合同，但只允许 `start`、`end`、`differenceType`，`start` / `end` 只写维度 grain、不要写 `measureId`，且只用于 `line`、`area`、`column`、`bar`、`columnParallel`、`barParallel`；
- `type: line` / `type: area` 标注的 annotation target 写法在本轮合同中不变。
- Step-level annotation 与 highlight 这里只额外约束它们在 scrollytelling 中只能描述当前步新增的视觉推进。
